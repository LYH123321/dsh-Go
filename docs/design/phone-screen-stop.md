# 手机操控：熄屏时的停止

2026-11-11。**未在真机上验证**，下面的行为依据源码和单元测试，真机要看的步骤在文末。

## 问题

1.0.14 起，熄屏会把正在跑的对话取消（#848、#926、#968）。进程和引擎都活着，是 App 自己发的取消：

```
熄屏 / 无障碍服务离开
  └─ PhoneTaskSessions.stopAll        对每个任务项上报 stopped，空闲的占位项也算
       └─ Dart phoneStopWatcherProvider   看到 stopped 的上升沿
            └─ 取消本机引擎上所有在跑的对话
```

1.0.13 的原生代码只在有手机任务在跑时才停，改成按会话批量停止时没带过来。

## 现在的行为

### 空闲时不上报停止

`PhoneTaskSessions.stopAll` 仍然让之前的持有者和已排队的准入失效，但对空闲的记录不再建立停止保持，也不把会话写进 `stoppedSessions`。判断在 `PhoneTasks` 的同一把锁里做：

- 在跑、已暂停、或仍有调用在执行的任务：走原来的 `stopLocked`，停止消息、30 秒保持、会话围栏、技能取消和资源清理都不变。
- 冷启动的占位项、已结束的、已按空闲投影的任务：只推进纪元并结束过期的 scope。

用户主动停止（悬浮条、通知）不受影响，仍然可以停止冷的或空闲的记录。

### 停止时由原生记下有没有打断任务

状态推送（`PhoneControl.emitStatus`）是在 ticker 线程上重新取样，不是事件队列。任务刚开始或刚结束时，Dart 手里相邻的两份状态可能都对不上实际情况。所以这件事由原生在停止的那一刻判定：

- `PhoneTasks.stopLocked` 在结束任务**之前**、在锁内记下当时任务是否在跑，随 `Snapshot.toMap` 以 `task.interrupted`（布尔）上报。
- 「在跑」用的是对外投影的 active，和 `snapshot().active` 同一口径：已暂停或仍有调用在执行的任务即使超过空闲时长也算在跑，只有按空闲投影的不算。
- 停止保持期内再次停止，不会把已经记下的 true 冲掉。
- 保持到期、成功进入下一个任务、`clearStop`、有效的 `resumeForSnapshot`、成功的 `finishScope` 之后清零。

`interrupted` 只是记录事实，不参与准入、清理或恢复。

### Dart 一侧

`PhoneTaskStatus.interrupted` 是可空布尔：

| 原生上报 | 解析结果 | 停止沿上怎么判 |
|---|---|---|
| 没有这个字段（旧版原生） | null | 回退：上一份或这一份状态里 `task.active` 为真 |
| 布尔值 | 原值 | 直接用 |
| 有字段但不是布尔 | false | 不取消，不回退 |

`phoneStopWatcherProvider` 里状态版本、launch 基线、`modernSeen` 的判断都没有变：全对话取消只发生在没用过按会话隔离的手机工具的那条旧路径上。

## 没有改变的

1. **准入围栏。** 每次 `stopAll` 仍对所有既有记录推进 `admissionEpoch`，旧的排队调用等到保持期之后也会被拒绝。
2. **持有者围栏。** 空闲分支推进 `lifecycle`；内部在跑但已按空闲投影的任务会走 `endLocked`，清掉原任务的批准、免确认、可视化授权和插话。
3. **批量提交的顺序。** 持锁时提交全部记录，再在锁外取消驱动和问答、发布快照、清理。
4. **重复通知不延长旧保持。** 第二次熄屏广播只让旧票据失效，保留第一次的 `stoppedUntil` 和原因，不产生新的上升沿。
5. **物理资源不提前释放。** `pending`、`running`、`cancelling`、`closing`、清理失败、日志和技能 scope 的结算门槛都不变。

## 已知的局限

- **状态通道不是事件队列。** 整个停止保持期都没被取样到，或者取样前已经被显式恢复，Dart 仍然看不到停止沿。`interrupted` 只解决「已经看到停止沿时，怎么判断有没有打断任务」。
- **熄屏后现代会话的手机工具保持「已停止」。** 在跑的任务因熄屏被停止后，会话留在 `stoppedSessions` 里，直到 `resume` 或 `retire`；30 秒只是任务级的保持，不是会话围栏的期限。亮屏解锁后自动恢复**没有实现**，见下一节。
- 退休记录里冻结的快照是历史，不能拿它的 `interrupted` 决定现在要不要取消。

## 没有做的：解锁后恢复可用

要做的话，需要满足这些条件，否则会让旧的调用复活：

- 给停止来源加类型（熄屏、用户、关开关、服务离开），不能靠 `stopReason` 的文案识别。两处熄屏入口（`PhoneControl.registerScreenOffNow`、`PhoneA11yService.screenOff`）都要明确传「熄屏」。
- 只恢复「仅因熄屏而被围栏」的会话；之后任何一次用户停止、关开关或服务离开，立即取消它的恢复资格。
- 解锁后只开放这个会话的**新一轮**。旧一轮的停止标记和准入纪元保留，不能直接调用现有的 `resume`（它会清掉记录级的停止，可能让旧一轮的重试复活）。不自动重试原动作，不继续旧的批准和免确认。
- 只有 `isEnabled() && !isLocked()` 时才尝试。亮屏不等于解锁：监听 `ACTION_USER_PRESENT`，无锁屏的设备在亮屏时重查；监听只是触发重查，不是凭证。
- 解锁可能早于清理结束，恢复检查要复用上面第 5 条的结算门槛。不跨引擎重启恢复。

## 无障碍服务的熄屏广播

`PhoneA11yService` 的熄屏广播在手机操控总开关关着时仍然生效，这里没有改。这个服务还承载桌宠和截屏的入口，`stopAll` 会先中止驱动、结束悬浮问答；总开关刚关上不代表之前的系统操作和提示已经排空，丢掉这条清理路径会留下新的空档。空闲时不再产生停止沿之后，这条广播对普通对话已经没有影响。

## 测试

- `PhoneTaskSessionsTest`：冷占位、未开始的现代准入、已结束的一轮、按空闲投影的旧任务、已暂停、连续两次广播不续期、在跑的现代会话围栏保持到显式恢复。
- `PhoneTasksInterruptedTest`：未送达「在跑」就停止、冷或空闲时的显式停止、正常结束后紧接停止、保持期内重复、到期后的冷停止、被拒绝的重试、新任务和显式清除、已暂停和有调用在执行的任务、空闲边界上的单次取样。
- `phone_stop_watcher_test.dart`：字段为 false 不取消、为 true 取消、类型不对不取消；没有字段时按相邻状态回退。

## 真机上要看的

记下机型、Android 版本、ABI。

1. 只有普通对话在跑、没有手机任务：熄屏，对话应继续。分别在手机操控开和关（无障碍服务仍连着）下各做一遍，连续熄屏解锁三次。
2. 本次引擎启动后用过一次手机工具，再重复第 1 步。
3. 手机任务正在操作主屏或后台屏时熄屏：任务应停止，旧动作不重试，资源在实际清理后释放。
4. 手机任务进行中在悬浮条上点停止：当前对话应结束。
5. 手机任务刚开始就熄屏：对话应取消。手机任务正常结束后立刻熄屏：对话不应取消。
6. 先手动停止再熄屏：不应因此恢复。
